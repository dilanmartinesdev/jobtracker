# Technical decisions

Each entry says what was chosen, why, and what it costs. Several of them exist because an audit found a real problem; those link to [audit.md](audit.md).

## Backend

### Routers, services and schemas are separate
Routers only translate HTTP. Business rules live in `services/`, which take plain arguments and raise domain exceptions (`ApplicationNotFoundError`, `EmailAlreadyRegisteredError`). `main.py` maps those exceptions to status codes.
*Why:* the rules can be tested and reused without HTTP (the seed script calls the same `create_user` the API does), and a router stays readable.
*Cost:* a few more files than a single `main.py`.

### Synchronous SQLAlchemy
Endpoints are plain `def`, which FastAPI runs in a thread pool. The work is database-bound and the data is small.
*Why:* async SQLAlchemy adds real complexity (async sessions, lazy-load pitfalls) for no measurable gain here.
*Cost:* each concurrent request occupies a thread. If the API ever needs thousands of concurrent connections, revisit.

### Argon2id for passwords, with a constant-time login
Passwords use Argon2id through `argon2-cffi`; hashes are upgraded on login when the parameters change. When an email is unknown, the code still verifies against a dummy hash, so the response time does not reveal which emails are registered.
*Why:* the first version used bcrypt, which fails on passwords over 72 bytes and crashed the endpoint with a 500 for long or emoji-heavy passwords. Argon2id has no such limit and is the current OWASP recommendation. The timing gap was measured at roughly 7 ms (unknown) against 290 ms (known).
*Cost:* a heavier hash means each login uses more CPU and memory; this is the point.

### JWT access tokens, no refresh tokens
Tokens carry only the user id, expire after 60 minutes and are checked for signature, expiry and required claims. In production, a missing or short `SECRET_KEY` stops the app from starting; in development a random key is generated, so there is no default secret to leak.
*Why:* simple, stateless, enough for a single-user-scoped app.
*Cost:* a token cannot be revoked before it expires, and users sign in again after an hour. Refresh tokens or server-side sessions would fix both.

### `404` instead of `403` for other people's data
Every service query includes `user_id`. Asking for someone else's application looks the same as asking for one that does not exist.
*Why:* a `403` confirms that the id exists.

### Status as `VARCHAR` + `CHECK`, not a native enum
*Why:* adding a stage is a normal migration. A native PostgreSQL enum needs `ALTER TYPE`, which cannot run inside a transaction on older versions and cannot remove values.

### Status history is a table, and the funnel is computed from it
Every stage change appends a row to `application_events`. The funnel counts applications that *ever* reached a stage (`COUNT(DISTINCT application_id)`).
*Why:* counting the current column makes an application that was rejected after an interview disappear from the interview rate, which understates how the search is going. The history also feeds the timeline in the UI.
*Cost:* one extra table and write per move.

### Reversing a move within two minutes erases it
If a change sets the status back to where the previous change came from, and that previous change is under two minutes old, the previous row is deleted instead of adding a second one.
*Why:* with "ever reached" semantics, dragging a card into Interview by accident and putting it back would raise the interview rate permanently. Found while reviewing screenshots; see the audit.
*Cost:* a deliberate, quick back-and-forth is also forgotten. Two minutes is long enough for a slip and short enough that real changes are kept.

### Timestamps are timezone-aware UTC everywhere
A small `TypeDecorator` (`UTCDateTime`) rejects naive datetimes on the way in and returns UTC on the way out, on every database.
*Why:* SQLite returns naive values, so the same code answered differently in tests and in production, and browsers read the naive string as local time.

### Alembic migrations, no `create_all()` at startup
The container runs `alembic upgrade head` before serving. A naming convention gives every constraint a stable name, and SQLite runs migrations in batch mode. CI runs `alembic check` so the models and migrations cannot drift.
*Why:* `create_all()` cannot change an existing table, so it fails the first time the schema evolves.
*Note:* the migration is self-contained. An earlier autogenerated one imported a type from the application code, which would break when that code changed.

### Tests run on SQLite by default and on PostgreSQL in CI
The same suite runs on both (`TEST_DATABASE_URL` switches).
*Why:* SQLite makes the local loop instant; PostgreSQL catches differences in types, constraints and case-insensitive search that SQLite hides.

### Login and sign-up are rate limited, in memory
10 requests per minute per client address, using `slowapi`.
*Why:* it stops password guessing at no infrastructure cost.
*Cost:* the counters are per process. With several API replicas the limit multiplies; a shared store (Redis) is the fix. Behind nginx, the real client address arrives in `X-Forwarded-For`; nginx overwrites that header instead of appending to it, and the API trusts it only because it is reachable solely through nginx.

### Sign-up says when an email is taken
`POST /auth/register` answers `409 Email is already registered`.
*Why:* a person who mistypes or forgets that they already have an account needs to be told. Hiding it needs email verification (send "if this is you, sign in" to the address), which needs a mail service this project does not have.
*Cost:* anyone can test whether an address has an account. Login does not leak this (same answer and same timing), and the sign-up route is rate limited, which slows bulk checking.

### Input is rejected, not repaired
Schemas forbid unknown fields, cap lengths, trim whitespace, turn empty strings into `NULL`, and accept only `http(s)` links.
*Why:* a stored `javascript:` link would run when someone clicked it. A field that cannot be set to `null` (company, role, stage, date) returns `422` on `PATCH`; before, it crashed with a `500`.

## Frontend

### TanStack Query for server state, with optimistic moves
*Why:* caching, refetching and rollback are solved problems. Moving a card updates the screen immediately and restores it if the server refuses, which keeps dragging responsive on a slow connection.
*Cost:* the cache rules (what to invalidate after each change) have to be right, which is why they live in one file (`api/hooks.ts`) and are tested.

### dnd-kit with mouse, touch and keyboard sensors
A few pixels of travel starts a mouse drag, so a plain click still opens the card. Touch needs a short press, so the board still scrolls with a finger. The keyboard sensor uses a custom coordinate getter so the arrow keys jump between columns. Screen-reader announcements are written in plain words.
*Why:* drag and drop that only works with a mouse excludes people and breaks on phones.

### Native `<dialog>` for the edit form
`showModal()` provides focus trapping, Escape to close and an inert page behind it.
*Why:* less code and fewer accessibility bugs than a hand-built modal.

### Plain CSS with design tokens, self-hosted fonts
No CSS framework. Colours, type and radii are variables on `:root`, with a dark theme that redefines them. Fonts (IBM Plex) come from npm packages and are served from the same origin.
*Why:* the interface is small; a framework would be more weight than the whole stylesheet. Self-hosting avoids a third-party request and lets the CSP forbid other origins.

### The access token lives in `localStorage`
*Why:* a refresh keeps the session without cookies, and an `Authorization` header is not sent automatically, so there is no CSRF exposure.
*Cost:* any script that runs in the page can read it. The mitigations are a strict Content-Security-Policy (only same-origin scripts, no inline script, no third-party origins), no rendering of raw HTML, and `http(s)`-only links. An `HttpOnly` cookie with CSRF protection is the stronger design and the next step if this grows.

### The interface is in English
*Why:* the audience is international employers. "Closed" is the label for the `rejected` status, which keeps the board neutral about an outcome the person may not call a rejection (a role filled internally, a withdrawn posting).

## Delivery

### One origin through nginx, with a strict CSP
nginx serves the built app and proxies `/api`. The CSP allows only same-origin scripts, styles, fonts, images and connections. `style-src-attr` allows the `style=""` attributes React sets for bar widths, while `<style>` blocks and external stylesheets stay forbidden.
*Verified:* the production build was loaded in a browser with exactly these headers and produced no violations. Vite is configured never to inline assets, because inlined fonts (`data:` URIs) were blocked by the policy.

### CI builds and starts the whole stack
The last job runs `docker compose up --wait` and calls the readiness endpoint through nginx.
*Why:* it proves the images, the migration on start-up and the proxy work together, which no unit test can.
